# Outreach Agent Instructions

These instructions apply to the whole repository. They are written for coding agents (Codex, Claude Code, etc.) that run the outreach workflows against the local API.

Do not run builds, tests, compilers, dev servers, preview servers, browsers, or process start/stop commands unless the user explicitly asks for that specific verification or runtime action. For UI/code edits, make the requested change and only inspect source files unless the user asks you to verify by building, testing, opening the app, starting a server, stopping a server, or restarting anything. If a server is already running, assume the user owns it and leave it alone unless they explicitly ask otherwise.

When the user asks for work such as "Run the pipeline for the Instagram profiles", "Start the pipeline for prospects", "Start the outreach pipeline", "Generate messages for prospects", "Fix messages for prospects", or "write inmails for influencers", treat that as the Prospecting workflow. Split the work into separate agents/subtasks whenever the tooling supports it, but only for the current five-profile batch; never dispatch work for a later batch while the current batch is still being crawled, updated, personalized, verified, reviewed, or marked ready. Keep the responsibilities separate even when subagents are not available. The Prospecting workflow always personalizes from the active DM template (kind=Dm) and never from the Email template. The Email template is only for the separate Email Follow-up workflow. If no DM template is currently active, stop and ask the user which DM template to activate; never substitute the Email template or any Email-kind body as the Prospecting source.

During the Prospecting workflow, do not use dynamic inline Node commands for local Outreach API calls, including `node -e` and heredoc/stdin forms such as `node - <<'NODE'`. This applies even when the command is read-only, such as `GET /api/creators/pending` verification with embedded prospect IDs. Use the stable helper commands below so reusable Codex approval prefixes can apply. If a needed Prospecting API action is not covered by an existing helper, create or extend a stable `.codex-*.mjs` helper first instead of running a one-off inline script.

For prospect record saves during the Prospecting workflow, avoid dynamic `node -e` API update commands. Put the per-run update payload in `.codex-prospect-save.json` and run the stable helper command `node .codex-prospect-save.mjs` from the Outreach repo root so the reusable Codex approval prefix can apply. The helper is intentionally limited to queued prospects and non-workflow fields; do not bypass it with inline scripts unless the user explicitly asks for a different update mechanism.

For read-only batch verification during the Prospecting workflow, including checks that prospects are still queued or that saved drafts remain queued, avoid dynamic `node -e` localhost API commands with embedded prospect IDs. Put the batch IDs or expected saved fields in `.codex-prospect-verify.json`, or reuse `.codex-prospect-save.json` after a save, and run the stable helper command `node .codex-prospect-verify.mjs` from the Outreach repo root so the reusable Codex approval prefix can apply. The helper is read-only and verifies that touched prospects are still queued and match expected saved fields.

For readiness QA during the Prospecting workflow, avoid dynamic inline API commands to mark prospects ready. Put the QA-passed prospect IDs in `.codex-prospect-ready.json` and run the stable helper command `node .codex-prospect-ready.mjs` from the Outreach repo root. The API will only mark queued prospects ready when follower count is set and the saved message is personalized enough to differ from the default template. This marks the prospect as ready for action only; it must not mark the prospect contacted or complete.

For crawler-only Instagram or TikTok profile fetches during the Prospecting workflow, avoid dynamic `curl <profile-url> | parser` commands. Put the exact provided profile URLs in `.codex-profile-crawl.json` and run the stable helper command `node .codex-profile-crawl.mjs` from the Outreach repo root so the reusable Codex approval prefix can apply. The helper is intentionally limited to HTTPS Instagram and TikTok hosts and must only be used with the exact profile URL already attached to the queued prospect. For Instagram, first request that exact profile-page URL and use it only when it returns profile-specific fields; a generic `Instagram` title is not useful evidence and must not be treated as a successful profile crawl. When the direct page is generic or incomplete, derive the username from the exact attached URL and try Instagram's `web_profile_info` API. When neither crawler method yields profile-specific data, immediately inspect the same exact attached URL through permitted rendered or logged-in rendered UI before reporting the profile blocked, incomplete, or unknown. Only if all three methods fail to expose the needed fields may the profile be reported as blocked/incomplete and receive a conservative fallback draft.

When the user asks for work such as "personalize follow-up emails", "generate email follow-ups", "write emails for creators who did not respond", "run the email follow-up workflow", or similar, treat that as the Email Follow-up workflow, not the Prospecting workflow. The Email Follow-up workflow starts from reached-out creators who have an email address and have not been contacted for at least 7 days unless the user gives a different threshold. Use the stable helper command `node .codex-email-followup-list.mjs --days 7` from the Outreach repo root to list candidates; do not use dynamic inline Node API calls for candidate discovery. The helper returns the previous personalized DM in `messageBody`, the DM template id in `messageTemplateId`, any existing email draft subject/body in `emailSubject` and `emailBody`, and the selected email template id in `emailTemplateId`.

During the Email Follow-up workflow, do not crawl Instagram or TikTok profiles, do not search the web, do not re-open profile URLs, and do not dispatch Profile Exploration, Data Update, or Missing Data Collector agents. Personalize the email from the active Email template subject/body and generation rules, the creator's existing CRM fields, and the previous personalized DM stored in `messageBody`. The previous personalized DM is the primary personalization source; preserve its truthful context and adapt it into a concise email follow-up. Do not invent new profile details, new language evidence, follower counts, emails, Threads links, response status, contact dates, or partnership outcomes. If the previous DM is missing or generic, write a conservative email using only known CRM fields and report that the prior personalized DM was unavailable. Save email drafts only to the email follow-up fields (`emailTemplateId`, `emailSubject`, and `emailBody`); do not overwrite the DM fields (`messageTemplateId`, `messageVersion`, or `messageBody`) and do not mark creators contacted, complete, sent, responded, or archived.

1. Orchestration Agent: coordinate the workflow only. Query or list the current queued prospects/pending influencers from the app/API, read the active DM template (kind=Dm) including both the message body and separate generation rules/AI rules — the Prospecting workflow always uses the active DM template and never the Email template, dispatch the required subagents, review their structured outputs, run read-only verification, and summarize what was done for the user. If profile data is missing or URL crawls are blocked/incomplete, dispatch one final Missing Data Collector Agent for only the affected profiles before final verification, then dispatch one Message Review Agent to review the personalized messages for those affected profiles. When the user explicitly asks to retry previously blocked or incomplete profiles, treat the Missing Data Collector Agent as the exploratory retry step, then run Data Update Agent and Message Personalization Agent only for those affected profiles using the collector findings. Because these crawl/update/draft batch tasks are simple and repetitive, explicitly ask each subagent to use low effort unless the user asks for a different effort level. The Orchestration Agent must not directly crawl profiles, invent data, write profile fields, write outreach drafts, mark prospects complete/contacted, or otherwise edit prospect records when subagent tooling is available.
2. Apply platform filtering only when the user explicitly asks for it. For example, "Instagram profiles" means only queued Instagram prospects, "TikTok profiles" means only queued TikTok prospects, and a generic "prospects" or "outreach pipeline" means all queued prospects.
3. Process prospects in strictly sequential batches of up to 5 profiles unless the user explicitly gives a different batch size. Do not use 6 or 7 as a default. Continue selecting the next in-scope queued batch until no in-scope queued prospects remain to be processed; the final batch may contain fewer than 5 profiles. For each batch, complete the full cycle before starting the next batch: Profile Exploration Agent crawls only those profiles, Data Update Agent applies factual updates for those same profiles, Message Personalization Agent drafts messages for those same profiles, Missing Data Collector Agent makes one last pass only when needed for profiles in that same batch with missing or blocked crawl data, Message Review Agent reviews drafts for affected profiles in that same batch when a collector pass was needed, the Orchestration Agent verifies that the batch remains queued with only intended changes, and Readiness QA Agent marks only eligible prospects from that same batch ready for action. Only after readiness QA and final verification for the current batch are complete may the Orchestration Agent select and crawl the next batch of up to 5 profiles. Do not dispatch exploration, update, personalization, review, verification, or readiness work for later batches while the current batch is in progress.
3a. Treat the first batch of every Prospecting workflow run as a mandatory crawler verification gate. Profile Exploration must obtain a visible, reliable follower count for every profile in that first batch before the workflow may dispatch Data Update, Message Personalization, Missing Data Collector, Message Review, follower cleanup, Readiness QA, or any later batch. If the crawler does not return a reliable follower count, continue using the Codex browser yourself; subagents cannot access the Codex in-app browser. If even one first-batch prospect still has no reliable follower count after that rendered-browser fallback, stop the entire workflow immediately, report the exact request/response evidence and access method, ask the user for help troubleshooting the crawler, and wait for the user's direction. Do not save fallback drafts, continue retrying batches, or crawl another profile until the crawler issue is resolved with the user.
4. Profile Exploration Agent: fetch information from the current batch of queued prospects in scope. For each prospect, crawl/open only the Instagram or TikTok profile URL that is already attached to that prospect record. Do not search for the person, guess alternate handles, open other social profiles, or use any profile URL other than the one provided in the app/API. For Instagram crawler-only access, first use the stable helper's exact profile-page request. If it is generic or lacks profile-specific data, try its `instagram-web-profile-info-api` result. If both crawler methods are generic, 401, or lack user fields, immediately open the same exact attached URL in permitted rendered or logged-in rendered UI. This rendered fallback is mandatory, not optional; do not report the crawl blocked or ask for generic fallback drafts until it has also failed or omitted the required fields. Return a structured summary for each prospect with the exact visible signals found, the access method used, and whether the profile was crawler-only, rendered, or logged-in rendered: display name, bio text, language, follower count if visible, email if visibly listed, Threads profile link if visibly linked from the exact provided profile URL, Threads username if explicitly mentioned in the bio/link area, and any partnership/code/promo clues. Language must be based on visible profile text such as bio, captions, profile UI text authored by the creator, or an explicit creator-stated location/language signal. An explicit creator self-identification with a language, country, or nationality may establish the likely audience language even when the phrase itself is in English: for example, `Swedish gym rat` supports Swedish and `Spanish gym rat` supports Spanish. Do not infer language from handle, display name, surname, appearance, ethnicity, country stereotypes, or weak name-pattern guesses. If visible creator-authored text is English or language-ambiguous and contains no explicit self-identification that establishes a likely non-English audience language, mark language as English or unknown instead of guessing another language. When checking Threads, look for both `threads.com` and `threads.net` links or profile badges, including rendered/logged-in UI when available. Instagram may hide Threads badges from crawler/server HTML, including behind flags such as `should_show_threads_badge_for_crawler:false`; crawler-only absence of a Threads token is not evidence that no Threads profile is exposed. If only crawler/server HTML is available and no Threads signal appears, mark Threads as unknown and report the access limitation. Update Threads only when the exact profile UI visibly exposes the Threads link or the exact profile bio/link area explicitly mentions a Threads username. If something is not visible or confidently parsed, mark it as unknown. If both crawler methods and rendered inspection provide only generic `Instagram` output or no user fields, treat the crawl as incomplete; do not ask Message Personalization to write handle-only drafts unless the user explicitly accepts generic fallback drafts.
5. Data Update Agent: update only factual prospect fields from the Profile Exploration Agent's structured summaries for the current batch. Add or update email address, follower count, and Threads link only when applicable and supported by explicit profile evidence. Update follower count only when it is visible and confidently parsed. Update email only when it is visibly listed on the exact provided profile URL and confidently parsed. Update Threads only when the exact Threads profile link is visibly available from the exact provided profile URL and confidently parsed, checking both `threads.com` and `threads.net`, or when a Threads username is explicitly mentioned in the exact profile bio/link area; if only an explicit Threads username is visible, normalize it to `https://www.threads.com/@username`. Do not invent or infer emails or Threads links from matching handles or profile conventions. Do not update response status, sent/completed state, first message date, last contact date, or any completion/contacted fields.
6. Message Personalization Agent: generate and save or attach a personalized outreach draft for each queued prospect in the current batch using only the active DM template body (kind=Dm), the active DM generation rules, existing prospect data, and the Profile Exploration Agent's structured summaries. Treat generation rules as instructions, not message copy. The creator-code economics must match the current active DM template at generation time; never hard-code an offer or carry forward economics from an older template version. Preserve existing factual fields unless the Data Update Agent explicitly updated them. Translate the draft when visible creator-authored profile text clearly supports that language, including an explicit self-identification with a language, country, or nationality that reasonably establishes a likely non-English audience language even if the identifying phrase is English, such as `Swedish gym rat` or `Spanish gym rat`. Do not translate based on handle, display name, surname, inferred nationality, appearance, or weak name-pattern guesses. If language is unknown, mixed, or only English text is visible without such an explicit self-identification, write the draft in English. When writing non-English outreach drafts, use natural native spelling and required diacritics/accent characters such as Swedish å/ä/ö, French accents, Dutch diacritics, and German umlauts; the codebase's default ASCII editing preference does not apply to user-facing outreach copy. Leave each prospect in the prospect queue; do not mark prospects complete/contacted automatically.
7. Missing Data Collector Agent: run only after the normal Profile Exploration, Data Update, and Message Personalization cycle when one or more affected profiles still have missing_or_blocked_fields or blocked/incomplete URL crawl results, or when the user explicitly asks to retry those affected profiles. In a retry, the Missing Data Collector Agent replaces the normal Profile Exploration Agent for the affected profiles. Make exactly one last collection pass for only those affected profiles and only the missing fields. Use only the exact Instagram or TikTok profile URL attached to the prospect record; do not search, guess alternate handles, open unrelated social profiles, or construct Threads/email/follower data from conventions. For Instagram retries, run the stable helper's exact profile-page request first, then its `instagram-web_profile_info` API if direct HTML is generic or incomplete. When both crawler methods are generic, 401, or lack profile-specific fields, the collector must inspect the same exact URL through rendered or logged-in rendered UI before concluding that a field is unavailable; generic HTML-only `Instagram` output alone is still incomplete data. Prefer a different allowed access method from the failed attempt when available, such as rendered or logged-in rendered UI, but report access limitations plainly if the exact URL still does not expose the missing data. Return structured findings with explicit evidence and access method. Any new factual fields found by this agent must go through the Data Update Agent before drafts are revised or reviewed.
8. Message Review Agent: run after the Missing Data Collector Agent for every profile that had missing or blocked crawl data. Review the saved personalized message against the current active template body, generation rules, existing prospect data, Profile Exploration Agent summary, Missing Data Collector Agent summary, and any Data Update Agent changes. Re-read the active DM template at review time and verify that the draft's creator-code economics match it exactly in meaning; never force a previously used percentage, payout period, or other offer term. Verify that the draft does not invent missing details, does not translate without visible creator-authored language evidence, does not include generation rules as copy, retains the template's compact creator-code closing without expanding it, uses natural native spelling and required diacritics for the chosen language, avoids prohibited punctuation such as em dashes, and leaves the prospect queued. Return a structured review result for each affected profile. If a draft needs correction, report the exact issue and dispatch Message Personalization Agent to save the corrected draft before final orchestration verification.
9. Follower Count Cleanup QA Agent: after all in-scope batches have completed the normal crawl, update, draft, missing-data, review, and orchestration verification cycle, check the touched queued prospects for missing follower counts. If any touched prospect still has no follower count because the initial crawl failed, was blocked, or did not expose a reliable value, dispatch one final cleanup QA agent for only those profiles and only the missing follower count. The cleanup agent must use only the exact attached Instagram or TikTok profile URL, must not search or guess alternate profiles, and must return explicit evidence and access method. Any follower count found by this cleanup pass must go through the Data Update Agent and stable save helper before final verification and readiness QA. If the exact URL still does not expose a reliable follower count, leave it unset and report that the prospect cannot be marked ready automatically.
10. Readiness QA Agent: after orchestration verification passes for the current 5-profile batch, and again after any final follower-count cleanup pass for that same batch, review only the touched queued prospects from that batch and mark them ready for action only when follower count is set and the saved message has been personalized from the default template. Use `.codex-prospect-ready.json` plus `node .codex-prospect-ready.mjs`; do not mark prospects contacted, complete, sent, or moved out of the prospect queue. Readiness QA is the last required step before the Orchestration Agent may start crawling the next 5 profiles.
11. Orchestration Agent verification: after each batch's subagents finish, read the queue and verify that every prospect touched by the batch is still queued, has the expected draft, has only the intended factual field updates, and has the expected ready-for-action state after QA. If any record is no longer queued or appears manually changed by the user, stop and report it instead of restoring, moving, overwriting the status, or continuing to the next batch.

Do not paste generation rules into the outreach draft unless the template body explicitly asks for that. Do not fabricate follower counts, profile details, emails, Threads links, response status, or sent dates. Instagram and TikTok may block, hide, localize, or omit follower counts, Threads badges, and profile links, so follower and Threads extraction is best-effort; leave the existing/manual follower or Threads value unchanged if the value is not visible or reliable. A Threads URL may be normalized from an explicitly mentioned Threads username in the exact profile bio/link area, but must not be constructed from the Instagram handle alone. If the provided prospect URL cannot be accessed, tell the user that access to that exact URL is blocked or unavailable and do not work around it by searching elsewhere. If a useful detail is missing, write the message without inventing it. Completion means the user has actually sent the message, so leave that final step to the user. Never restore a prospect to queued, move a prospect between workflow states, or undo a status/contact-date change unless the user explicitly asks for that exact correction.

Use the active DM template's creator-code and closing language as written. Do not expand it with trust-based long-term partnership, one-off-ad, rigid-campaign, or natural/effective-sharing boilerplate unless the active template body explicitly contains that copy.
